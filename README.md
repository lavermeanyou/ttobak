# 또박 — 눈으로 보는 한국어 발음 연습 (MVP 데모)

선천성 청각장애·인공와우 사용자가 자기 발음을 **귀 대신 눈으로** 확인하도록, 녹음 한 번으로 "어느 소리가 무엇처럼 들렸는지"를 음절 색, 교정 문구, 높낮이 선, 입모양 판정으로 보여 주는 웹 데모입니다.

> 판정의 중심은 음성입니다. 입술(카메라)은 보조 판정과 따라 하기 안내에만 씁니다.
> 의료기기가 아니며 진단·치료 목적으로 쓸 수 없습니다(아래 [한계](#한계) 참고).

---

## 실행 방법

### 1) 설치 (macOS 기준, Python 3.12)

```bash
cd ttobak
python3.12 -m venv .venv
.venv/bin/pip install -r requirements.txt   # 검증한 버전으로 고정(torch 2.14.1, torchaudio 2.11.0, transformers 5.19.0 …)
brew install ffmpeg                         # 브라우저가 wav 가 아닌 형식을 보낼 때 변환용(없어도 wav 는 동작)
```

### 2) 서버 실행 (모델 자동 내려받기)

```bash
bash scripts/run.sh                 # 모델이 없으면 내려받고(약 1.2 GB, 한 번만) http://localhost:8765 로 띄운다
PORT=9000 bash scripts/run.sh       # 다른 포트
```

인식 모델은 [`slplab/wav2vec2-xls-r-300m_phone-mfa_korean`](https://huggingface.co/slplab/wav2vec2-xls-r-300m_phone-mfa_korean)이고 `models/ko-phone/`(`.gitignore` 대상)에 받습니다. 직접 받으려면:

```bash
.venv/bin/python -c "from huggingface_hub import snapshot_download; \
snapshot_download('slplab/wav2vec2-xls-r-300m_phone-mfa_korean', local_dir='models/ko-phone')"
.venv/bin/uvicorn server.app:app --port 8765          # 다른 위치에서: --app-dir /경로/ttobak
```

### 3) 서버가 켜진 뒤

- 모델은 서버가 켜질 때 백그라운드에서 올라갑니다(Apple Silicon 기준 약 5~10초, `mps` 자동 사용). 올라가는 동안 `GET /api/health`는 `{"model":"loading"}`을 돌려주고, 분석 요청은 503과 함께 "준비하고 있어요" 안내를 받습니다.
- 모든 파일 경로는 코드 위치(`Path(__file__)`) 기준이라 실행 위치와 상관없습니다.
- 목표 문장은 200자·120음소(약 50음절)까지 받습니다. 그보다 길면 분석 시간이 음소 수의 제곱으로 늘어(29.5초 녹음 기준 100음소 6초, 150음소 22초) `too_long`으로 거절합니다.

### 4) 브라우저

- **Chrome을 권장**하고 주소는 **`http://localhost:8765`** 로 엽니다. 마이크와 카메라는 보안 문맥(localhost 또는 https)에서만 켜집니다. 다른 기기에서 IP 주소로 접속하면 카메라와 마이크가 막힙니다.
- 입술 추적(MediaPipe Face Landmarker)은 `web/vendor/`의 로컬 파일을 먼저 쓰고, 없으면 CDN에서 받습니다. 글꼴(Google Fonts)만 인터넷이 필요하며, 오프라인이면 시스템 글꼴로 표시됩니다.
- 백엔드 없이 화면만 보려면 `http://localhost:8765/?mock=1` 로 엽니다(`web/dev/mock.js` 목업 응답).

### 5) 테스트·샘플·사람 음성 평가

```bash
.venv/bin/python -m pytest server/tests -q      # 전체 2874개 (2872 통과, 2 xfail = 미처리 G2P 규칙 기록)
bash scripts/make_samples.sh                    # 데모 샘플 wav 다시 만들기(macOS say, Yuna 음성)
.venv/bin/python -I scripts/eval_human.py all   # 사람 낭독 음성 오탐률: 내려받기(.review/human/) → 분석 → 요약 (약 20분)
.venv/bin/python -I scripts/eval_human.py report  # 저장된 결과로 요약만
```

### 분석 파이프라인 (`pipeline.analyze`)

| 단계 | 하는 일 | 모듈 |
|---|---|---|
| 1. 목표 만들기 | 철자 → 발음형([궁물]) → 음소열 `G U NG M U L`, 음절, 음절별 입모양 | `g2p`, `words` |
| 2. 오디오 정리 | 임의 형식 → 16 kHz mono float(위상이 반대인 스테레오는 큰 채널 하나). 0.15초 미만이거나 30초 초과면 `bad_audio`. 최대 강도와 유성 구간 길이로 `no_speech` 판정. 말소리 앞뒤 무음이 0.75초보다 길면 그만큼 잘라 인식기에 넣는다(시각은 원래 녹음 기준) | `pipeline`, `app` |
| 3. 방출확률 | wav2vec2 CTC log-softmax (앞뒤 0.5초 무음 문맥을 덧대 첫·끝 음소 누락 방지) | `recognizer.emissions` |
| 4. 발음 변이 선택 | 표준 허용 발음([시게]), 이어 말하기([밤머거요]) 후보 중 음성에 가장 그럴듯한 것을 목표로 채택 | `pipeline.choose_variant` |
| 5. 자유 인식 | greedy CTC: "무엇이 들렸나" 원본(판정에는 쓰지 않음). 목표 음소의 30 % 미만만 찾으면 `no_speech`(험·순음) | `recognizer.decode` |
| 6. 강제정렬 + GOP | 목표 음소별 시간 구간, CTC-GOP 점수, 가장 그럴듯한 대안 음소(alt) | `recognizer.force_align` |
| 7. 정렬 | 목표 대 자유 인식 편집 연산(match/sub/del/ins) | `align` |
| 8. 음소 상태 | CTC margin 과 '정상 변이' 규칙으로 `ok/weak/sub/del` 결정. 삽입은 CTC로 다시 확인된 문장 안쪽 것만 채택 | `pipeline.decide_status` |
| 9. 음향 | F0·강도 곡선, 음높이 폭, 끝 억양(반음), 모음 포먼트 | `acoustic` |
| 10. 입술 | 음소 구간별 입모양 판정, 입술 점수 | `lips` |
| 11. 요약 | 점수(overall/accuracy/clarity/intonation/lips), 피드백 카드 | `feedback.summarize` |

한 번 분석하는 데 Apple Silicon(mps) 기준 약 70~120 ms가 걸립니다(1~2초 길이 녹음).

## 판정 방식

### 1. CTC-GOP (음소마다 "목표대로 들렸나")

- 모델이 낸 프레임별 음소 확률로 **음소열 전체의 확률** log P(목표 음소열 | 음성)을 `ctc_loss` 한 번(배치)으로 계산합니다.
- 위치 i마다 그 자리만 **다른 39개 음소로 바꾸거나 뺀** 음소열의 확률도 함께 구해, 가장 그럴듯한 대안을 `alt`로 둡니다.
- `margin = log P(목표) − max log P(대안)` (단위 nat). 양수면 목표대로, 음수면 대안처럼 들린 것입니다.
- `gop = 100 · sigmoid(margin + 1.0)`. 사람 낭독 정상 음소는 90 %가 84점 이상(margin 중앙값 6.4)이고, 데모 오류 흉내의 틀린 자리는 2점 미만입니다.
- 상태 규칙(아래 6절의 사람 음성 실측으로 정함):
  1. `alt`가 **정상 변이**이면 → `ok` (아래 목록)
  2. `margin < −3.0` → 대안이 뚜렷이(약 20배) 더 그럴듯함 → `sub`(들린 소리 = alt) 또는 `del`(alt = 빠짐)
  3. `gop < 45`(margin < −1.2) → `weak`(애매함, 정보 카드)
  4. 그 밖 → `ok`
- 정상 변이(표준발음이나 자연스러운 이어 말하기로 설명되는 소리 — 사람 낭독 오탐에서 찾음):
  - 받침 ㄱ·ㄷ·ㅂ 뒤 예사소리↔된소리: 했다[핻따]의 ㄸ을 ㄷ으로 들음(예전 오탐 1위)
  - 공명음 받침 뒤 '된소리되기 자리'(철자는 예사소리)의 예사소리: 결정[결쩡]을 [결정]으로
  - 모음·공명음 뒤 ㅎ 약화·탈락: 전화[저놔], 결혼[겨론] (발화 첫 ㅎ은 그대로 판정)
  - 받침 ㄱ·ㄷ·ㅂ이 뒤 된소리·거센소리와 겹치거나 위치가 바뀜: 있고[익꼬], 받침 ㄴ·ㅁ 위치 동화: 연구[영구]
  - 어절 끝 조사 '에'↔'의'(실제로는 둘 다 [에])
- 자유 인식(greedy CTC)은 판정에 쓰지 않습니다. 사람 낭독에서 자유 인식을 함께 쓰면 오탐이 두 배였습니다(sub+del 2.9 % → 6.7 %).
- 삽입: 자유 인식에만 있는 음소는 그 음소를 끼운 음소열이 4.0 nat 넘게 더 그럴듯할 때만 채택합니다(ㅡ는 1.0). 발화 맨 앞과 맨 뒤의 덧소리는 숨소리·잡음과 구별할 수 없어 판정하지 않습니다. 단 받침으로 끝나는 말 뒤의 'ㅡ'(앞→아프)는 실제로 흔한 오류라 판정합니다.
- 어절 사이 이어 말하기(밥 먹어요[밤머거요], 일 년[일련])와 허용 발음(시계[시게])은 대안 발음형 가운데 음성에 가장 그럴듯한 것을 목표로 골라 오류로 보지 않습니다.

### 2. 강제정렬 (음소의 시간 구간)

- CTC 비터비를 numpy로 직접 구현했습니다(`torchaudio.functional.forced_align` 제거 예정에 대비).
- 이 모델은 마지막 음절 스파이크를 입력 맨 끝 무음에 몰아서 내는 버릇이 있습니다. 그래서 시각용 정렬은 **에너지로 잡은 소리 구간 ±40 ms 안에서만** 음소가 나오게 제한하고, GOP는 제한 없는 확률로 계산합니다.
- CTC는 음소마다 1~2프레임만 내고 나머지는 blank입니다. blank 구간은 양쪽 음소 확률의 누적합이 최대가 되는 점에서 나누고, 60 ms 이상 무음은 쉼으로 보아 경계에 씁니다. 파열음의 폐쇄 구간과 받침 불파음 뒤 무음은 최대 120 ms까지 그 음소에 붙입니다.
- 이 구간이 포먼트 측정 창, 입술 판정 창, 차트의 음소 띠에 그대로 쓰입니다.

### 3. 입술 판정 규칙 (보조 판정, 너그럽게)

브라우저가 MediaPipe로 프레임마다 `open`/`width`(양 눈 바깥꼬리 거리로 정규화)와 블렌드셰이프 `pucker/funnel/jaw/close`를 보냅니다. 녹음 직후 0.6초 동안 "입 다물고 기다리기"로 기준값(neutral)을 잡습니다.

| 목표 입모양 | 해당 음소 | 통과 기준 |
|---|---|---|
| `round` 둥글게 | ㅗ ㅜ ㅛ ㅠ ㅘ ㅝ … | 최소 너비 ≤ 기준 너비의 90% 또는 max(pucker, funnel) ≥ 0.25 |
| `spread` 옆으로 | ㅣ ㅡ ㅔ … | 너비 중앙값 ≥ 기준의 97% 이고 pucker 75백분위 < 0.35 |
| `open` 크게 벌림 | ㅏ ㅑ | 최대 open ≥ max(0.08, 기준 + 0.06) 또는 jaw ≥ 0.25 |
| `closed` 다묾 | ㅂ ㅃ ㅍ ㅁ | 구간 경계 ±60 ms 안에서 open ≤ 기준 + 0.015 또는 close ≥ 0.3 |

- 모음은 구간 **가운데 50%** 만 봅니다. 경계 근처는 이웃 음소 입모양이 이어지는 동시조음 구간이기 때문입니다.
- 프레임이 모자라거나 애매하면 판정을 생략합니다(오판보다 생략). 입술 데이터가 없으면 `available:false`이고, 점수는 입술 항목을 빼고 가중 평균합니다.

### 4. 포먼트 (모음 입 벌림·혀 위치)

- Praat Burg 알고리즘(`to_formant_burg`)을 씁니다. 최대 포먼트 주파수는 남 5000, 여 5500, 아동 6500 Hz입니다. 강제정렬 모음 구간의 F1(입 벌림), F2(혀 앞뒤)를 성별·연령별 참고치(`phones.FORMANT_REF`)와 비교합니다.
- 허용 폭은 기본 F1 ±25%, F2 ±20%입니다. 화자 변이가 큰 모음(ㅏ의 F2, ㅜ 전설화, ㅗ/ㅜ 근접)은 그 방향만 넓혔습니다. 치조·경구개 자음 옆 모음은 F2가 끌려 올라가므로 F2 상한을 두지 않습니다.
- 이중모음은 구간 뒤쪽 1/3을 도착 모음 참고치와 비교합니다. 50 ms 미만 구간은 측정하지 않습니다. 인식은 정확한데 포먼트가 다른 모음 자리로 크게 튀면 측정 실패로 보고 숨깁니다.
- 포먼트는 **시각화와 보조 근거**로만 쓰고, 음소 오류 판정은 GOP가 합니다.

### 5. 점수와 피드백 카드

- `accuracy` = 음소 상태 점수(ok 1, weak 0.6, sub/del 0)의 평균 − 삽입 1개당 0.5음소
- `clarity` = GOP 평균
- `intonation`: 판정 의문문("좋아요?")은 끝 0.3초 상승이 +2반음 이상이면 좋음. 설명 의문문("뭐예요?")과 인사는 올려도 내려도 됨. 평서문은 음높이 폭 2~12반음이 좋고, 끝이 +4반음 이상 오르면 질문처럼 들린다고 안내
- `overall` = accuracy 0.5 + clarity 0.25 + intonation 0.1 + lips 0.15 (없는 항목은 빼고 다시 정규화)
- 카드 우선순위: (녹음이 찌그러졌으면 그 안내가 맨 앞) > 평음·격음·경음, ㅅ/ㅆ 대비 > 그 밖의 자음 대치(과비성·ㄹ·받침) > 탈락 > 모음 > 입모양 > 약함 > 억양·크기. 카드는 최대 4장까지 냅니다. '약함(weak)' 카드는 정상 화자에게도 나오는 애매한 자리라 정보(info) 수준입니다. 교정 문구는 귀로 들어 보라고 하지 않고 촉각·시각 단서를 씁니다(입 앞 휴지의 흔들림, 콧방울의 떨림, 거울 속 입술, 화면의 높낮이 선).

### 6. 사람 음성으로 맞춘 기준과 오탐률 (실측)

`scripts/eval_human.py`로 Hugging Face [`Bingsu/zeroth-korean`](https://huggingface.co/datasets/Bingsu/zeroth-korean) test split(CC BY 4.0, 16 kHz 성인 뉴스·소설 낭독)에서 숫자·영문이 없는 240문장(남녀 여러 화자 — F0로 본 화자 묶음 6개 안팎)을 받아 **정상 발음으로 보고** 잰 오탐률입니다. 화자가 겹치지 않도록 행 번호로 나눠 보정셋(117문장)으로 문턱을 정하고 검증셋(123문장)으로 확인했습니다. '오류 카드'는 소리(음소·삽입)에 대한 error·warn 카드입니다(칭찬·억양·크기·입술·정보 카드 제외).

- **단어 목표(오류 카드 15 % 미만)는 달성하지 못했습니다.** 같은 어절을 문장 속에서 판정하면 오류가 1개라도 있는 어절이 12 %인데, 잘라 내면 40 %로 늘어납니다. 잘라 낸 단어의 오탐 56 %가 첫·끝 음소에 몰려 있고(이웃 어절과 이어지던 전이 구간이 잘림), 문맥을 잃은 빠른 낭독체 단어는 사람도 알아듣기 어렵다고 알려져 있습니다(Pollack & Pickett, 1963). 실제 데모처럼 한 단어를 또박또박 단독으로 말한 녹음은 이 조건보다 나을 것으로 보지만 확인하지 못했습니다.
- 정상 변이로 인정한 음소는 문장 음소의 1.7 %입니다(받침 뒤 된소리 112, ㅎ 약화 96, 위치 동화 57, 된소리되기 자리 40, 받침 겹침 36, 조사 에·의 33).
- 남은 오탐: 모음 혼동(ㅗ↔ㅜ, ㅓ↔ㅏ·ㅗ, ㅡ→ㅣ), 빠른 말에서 ㅣ·ㅡ 탈락, 원순모음 앞 ㄱ→ㅂ, 받침 ㄴ·ㄹ 탈락 — 대부분 margin −3 ~ −8로 모델이 실제로 다른 소리를 들은 경우(모델 한계)입니다.
- **오류 검출률(대가)**: macOS 합성음 9종 × 최소대립쌍 44개(오류 낱말을 말한 음성 373건)에서 오류 자리를 sub/del/삽입으로 잡은 비율은 90.6 % → 76.7 %(Yuna 97.7 % → 88.6 %)로 줄었습니다. 대신 같은 음성의 정상 낱말은 통과하고 오류 낱말만 잡은 짝은 43.0 % → 51.7 %로 늘었습니다(정상 합성음도 그 자리를 오류로 듣는 경우가 많아 예전의 높은 검출률은 '구별'이 아니었음). 데모 오류 흉내 샘플 9개는 모두 그대로 잡습니다(오류 자리 margin −5.5 ~ −8.6).

## 한계

- **사람 정상 낭독으로 오탐률을 쟀지만, 인공와우 사용자의 발화로는 검증하지 못했습니다.** 판정 문턱(sub −3.0 nat, weak gop < 45 = margin −1.2, 삽입 4.0 nat)과 정상 변이 규칙은 일반 성인의 뉴스·소설 낭독(zeroth-korean 240문장)으로 정했습니다. 인공와우 사용자의 발화는 모음 중앙화, 비성, 느린 속도, 음질이 달라 같은 문턱이 맞는다는 근거가 없습니다. 언어치료사가 판정한 정답(평가자 간 일치도 포함)과 비교해야 합니다.
- **오류 검출률은 합성음 흉내로만 쟀습니다.** 오탐을 줄인 대가로 합성음 오류 흉내 검출률이 90.6 %에서 76.7 %로 낮아졌습니다(정상과 오류를 '구별'한 비율은 43 % → 52 %로 올랐음). margin −1.2 ~ −3.0 의 애매한 치환은 오류가 아니라 '약함'(정보 카드)으로만 보여 주므로, 덜 뚜렷한 실제 오류는 놓칠 수 있습니다. 실제 오류 녹음으로 민감도를 다시 재야 합니다.
- **단어 하나를 단독으로 말한 사람 녹음으로는 재지 못했습니다.** 문장에서 잘라 낸 단어로 잰 '오류 카드가 하나라도 나오는 단어' 비율은 약 42~44 %입니다(목표 15 % 미달). 같은 어절을 문장 속에서 판정하면 12 %라서 잘라 내기 자체(이어지던 전이 구간이 잘림, 문맥 상실)가 큰 몫이지만, 단독 발화에서도 첫·끝 음소에서 모델이 흔들릴 수 있습니다. 발표 전에 발표자 목소리로 연습 단어를 몇 번 녹음해 보길 권합니다.
- **모델의 체계적 오인식.** 사람 낭독에서도 모음 혼동(ㅗ↔ㅜ, ㅓ↔ㅏ·ㅗ, ㅡ→ㅣ), 빠른 말의 ㅣ·ㅡ 탈락, 원순모음 앞 ㄱ→ㅂ, 받침 ㄴ·ㄹ 탈락이 남습니다. 합성음(Yuna)에서는 어두 평음 ㅂ/ㄷ/ㄱ을 격음으로, 단어 끝 받침 ㄹ을 '리'로 듣는 경향이 있어 불·국물·과자·바다의 정상 합성음은 정상 샘플에서 뺐습니다. 이 모델은 앞뒤 무음 길이에도 민감합니다(같은 '소리'의 ㅗ margin이 무음 0.3초에서 −1.5, 0.4초에서 +1.6).
- **정상 변이 규칙은 진짜 오류도 가립니다.** 받침 뒤 된소리를 예사소리로, 모음 사이 ㅎ을 빼고, 받침 ㄴ을 ㅇ으로 동화해 말해도 오류로 보지 않습니다. 이런 자리의 정밀 교정이 목표라면 규칙을 끄고 따로 연습해야 합니다.
- **미처리 G2P 규칙.** 사이시옷의 원칙 발음(냇가→[내까]; 지금은 허용 발음 [낻까])은 사전에 있는 낱말만 처리합니다. 사전에 없는 낱말의 제24·26·28·29항(한자어 경음화, ㄴ 첨가 등)은 추정 후보로만 다루고, 자모 이름의 연음(디귿이→[디그시])은 처리하지 않습니다. 자유 입력 문장은 발음형이 틀려 정상 발음이 오류로 나올 수 있습니다.
- **과비성(콧소리 섞임)과 음질(쉰소리·거친 소리)은 측정하지 않습니다.** "ㅂ이 ㅁ처럼 들려요" 같은 과비성 카드는 음소가 비음으로 바뀌었을 때만 나옵니다. 비음치(nasalance), 모음의 비음화 정도, HNR·jitter·shimmer 같은 음질 지표는 아직 없습니다.
- **작은 소리는 거절합니다.** 25 ms 창 최대 크기가 −50 dBFS 미만이면 `no_speech`로 안내합니다. 실측상 신호 대 잡음비가 25 dB 아래로 떨어지면 정상 발음도 오류로 바뀌기 시작해, 너무 작은 녹음은 분석하지 않는 편이 낫습니다(브라우저 자동 음량 조절은 꺼 둠).
- **입술 판정은 카메라 조건에 민감합니다.** 고개를 돌리거나 숙이면 입 너비와 벌림이 틀어지고, 블렌드셰이프 기본값이 사람마다 다릅니다. 입술 영상이 소리보다 120 ms 넘게 늦으면 ㅣ 같은 짧은 모음 판정이 틀어질 수 있습니다. 그래서 문턱을 너그럽게 잡았고 애매하면 판정을 생략합니다.
- **포먼트 참고치는 성인 평균값입니다.** 개인차가 ±15~25%로 커서 모음 판정의 근거로는 쓰지 않고 시각화에만 씁니다. 아동 참고치는 근사값입니다.
- **의료기기가 아닙니다.** 진단, 치료, 청능재활 처방을 대신하지 않으며 언어치료사의 지도를 보조하는 연습 도구 시제품입니다. 카메라 영상은 서버로 보내지 않고 입술 수치만 보냅니다. 녹음은 분석에만 쓰고 저장하지 않으며, 시도 기록은 브라우저 localStorage에만 남습니다.
